# 2026-06-22 QoS 修复与 smoke 阻塞说明

## 一句话结论

**smoke 失败不是 TCP 隧道没连上，而是 Manjaro 上 `image_tcp_server` 用错了 ROS2 QoS，ZED 图根本进不了 server，Ubuntu 端 5 秒等不到帧就 `_queue.Empty`。**

---

## 你看到的两条日志其实是一件事

### Manjaro（ZED 侧）

```
[WARN] [zed_camera_node]: New subscription ... incompatible QoS.
Last incompatible policy: RELIABILITY
```

| 角色 | QoS Reliability |
|------|-----------------|
| `zed_camera_node` 发布 `/zed/left/image_raw` | **BEST_EFFORT**（相机标准做法） |
| 旧版 `image_tcp_server` 订阅 | **RELIABLE**（`create_subscription(..., 10)` 默认） |

ROS2 规则：**发布端与订阅端 reliability 不一致 → 不投递任何消息**。  
所以 ZED 日志里 FPS 正常（13–15），但 `image_tcp_server` 的 `_latest_jpeg["f"]` 一直是空的。

### Ubuntu（smoke 侧）

```
[image tcp] ready 127.0.0.1:32087   ← TCP 已连通，不能说明有图
...
_queue.Empty in video_capture.py   ← 读线程 5s 内没往 queue 里放过一帧
```

数据链：

```mermaid
flowchart LR
  ZED["ZED BEST_EFFORT"] -->|QoS 不匹配| X["image_tcp_server 收不到"]
  X -->|JPEG len=0| Bridge["ImageTcpBridge"]
  Bridge -->|fetch_bgr=None| TcpCap["TcpImageCapture"]
  TcpCap -->|read 失败| VCap["VideoCapture 队列空"]
  VCap -->|get timeout 5s| Err["_queue.Empty"]
```

## 已做的修复（本地 + 已 scp 到 Manjaro）

### 1. `python3.x/image_tcp_server.py`（Manjaro 运行）

订阅改为 `qos_profile_sensor_data`（BEST_EFFORT + KEEP_LAST），与 ZED / 鱼眼一致：

```python
from rclpy.qos import qos_profile_sensor_data
self.create_subscription(Image, topic, cb, qos_profile_sensor_data)
```

已通过 `deploy_manjaro_image_server.sh` 同步到：

`~/workspace2025/src/inspire_gripper/image_tcp_server.py`

### 2. `serl_robot_infra/franka_env/camera/ros_capture.py`

同样改为 `qos_profile_sensor_data`（以后若在 Ubuntu 本机 ROS 取图也不会踩坑）。

### 3. `serl_robot_infra/franka_env/camera/video_capture.py`

读线程在 `read()` 暂时失败时 **sleep 重试**，不再 `break` 退出（避免启动瞬间无帧就把线程弄死）。

## 优劣势（修复方案）

| | 说明 |
|--|------|
| **优势** | 改一行 QoS 即对齐相机惯例；不改 TCP 协议；Ubuntu 仍无需 ROS2 |
| **风险** | BEST_EFFORT 可能丢个别帧（15Hz 训练可接受）；旧 server 进程未杀会导致新 server 起不来 |

**置信度**：根因 = QoS 不匹配 → **高**（WARN 与 Empty 时间线、ROS2 语义完全一致）。
